# Agent Note: `registerConfig`'s exact-path watcher could miss a rapid second change

Status: implemented

## Problem

`node 24 / snapshots and artifacts` failed `apps/cli/tests/built-bin.e2e.ts`'s custom-profile hot-reload case on real hosted CI, timing out waiting for the `ready` marker to reappear after the test's "removal reverts" step (writing `[]\n` back to a profile's `cordis.patch.yml` right after a prior generation-2 override had already gone through one successful reload cycle). Reproducing in a from-scratch Linux container (matching the hosted runner) confirmed this is a genuine, non-environmental flake: solo, unloaded runs of just this test failed ~30% of the time (6/20), including runs that took the full 20s timeout with no other process contention.

Temporary debug logging through the whole reload path (`vendor/hmr`'s `registerConfig`/`refreshConfig`, `packages/boot/app-boot`'s `watchUserPatches` refresh callback, `vendor/include`'s `internal/update` handler) captured a failing run's trace: the first write (generation 2) produced a matched `onChange` → `refreshConfig` → `entry.update` → `root.update` cycle that completed correctly and rewrote `ready`. The second write (`[]\n`) never produced a matched `onChange` event at all — raw `fs.watch`'s notification for that exact path was silently dropped, not merely delayed. The application logic downstream (patch composition, serialized applies, fresh `structuredClone` per apply) was never reached because the event never arrived.

## Decision

**Force `usePolling: true` (100ms interval) on `registerConfig`'s exact-path config watcher**, overriding whatever the host's HMR config otherwise requests for the main content watcher. This watcher covers a handful of config files at most (a profile's and the home-level `cordis.patch.yml`), so stat-polling's overhead is negligible, and it removes the dependency on OS-level inotify/fs.watch event delivery being reliable for a single exact path watched independently of the main recursive content watcher.

**Superseded** (same day, before this PR merged): the real hosted `node 24 / coverage` job — which runs the whole suite under `--coverage` with only 2 CPUs available — failed `packages/boot/app-boot/tests/user-patches.spec.ts`'s add-detection test. Reproducing that load locally (a from-scratch Linux container, `vitest run --coverage --maxWorkers=2` pinned to 2 CPUs via `taskset`) didn't hit that exact test but did catch `hmr-config.spec.ts`'s disposal-serialization test failing the same way: `observed` was `['one']` instead of `['one', 'two']`. Root cause: chokidar's `usePolling` mode watches the whole parent directory, not just the target file — new-file detection goes through its `_handleRead` directory-readdir scan, which has its own hardcoded 1000ms per-directory throttle inside chokidar itself, on top of which our 100ms `interval` and the directory's own polled-mtime check both have to land inside a busy single-threaded worker's timer queue. Under `--coverage`'s real CPU contention (many concurrent tests, each with their own chokidar watcher/timers competing for the same 2 cores), that stack of scheduling dependencies occasionally pushed detection past a test's own fixed timing margin (250ms for the disposal test, 10s for the add-detection test) — a strictly worse regression than the bug it fixed, since it now touches every test that calls `registerConfig()`, not just the one rapid-second-edit case. Replaced with the design below.

**Final fix: keep the watcher on native (non-polling) `fs.watch`, and layer a lightweight periodic re-stat of just the one exact path on top of it as a safety net** — not instead of the live watcher, in addition to it. A `captureSnapshot()` helper (`{ mtimeMs } | 'missing'`) is primed once via `stat()` before the chokidar watcher opens, updated whenever the live watcher's `onChange` fires, and independently re-checked every 200ms via `ctx.interval()`; if the re-stat sees a snapshot that doesn't match the last-known one, it fires the same `refreshConfig()` path the live watcher uses. This keeps native fs.watch's near-instant delivery as the common path (satisfying tests that assume sub-second detection), while bounding the rare missed-event case to one 200ms poll interval instead of an indefinite hang — at the cost of one `stat()` call per 200ms per registered config, not a whole extra directory-watching subsystem per config.

## Consequences

Validated in the same Linux container: 20/20 then 15/15 repeated runs of the previously-flaky test passed with the `usePolling` fix (versus 6/20 failures before), and the full `apps/cli/tests/built-bin.e2e.ts` suite (18/18) still passed, including the other hot-reload-touching cases (`reports a patch-overlay boot failure without hanging`, `keeps the app arguments across a user patch reload`). That fix was then superseded by the re-stat safety net (see Decision) once real hosted CI load exposed its regression; the main content watcher (module hot-reload, potentially many files) was never touched by either version — only the exact-path config watcher changes.

## Alternatives considered

**Retrying the write from the test.** Rejected: the missed event is a real product-facing reliability gap (a user's second rapid config edit could just as well go unnoticed until their next edit), not a test-only artifact — fixing the watcher is the root cause, not the symptom.

**Debouncing or coalescing at the `onChange` layer.** Rejected: the event was never delivered at all, not delivered twice or out of order, so no amount of debounce/coalesce logic downstream of the raw `fs.watch` listener can recover it.

**Forcing `usePolling: true` on the whole watcher.** Tried first, worked in isolation, but regressed under real CI parallel load (see Decision) — kept as an object lesson: directory-level polling adds throttled, timer-scheduled latency that's cheap to eyeball as "negligible" from a low-contention container run and expensive in practice under a loaded CI runner. The re-stat safety net targets only the one path that actually needs the guarantee.

## Verification

Linux container (matching the hosted runner): 20/20 and 15/15 repeated runs of `built-bin.e2e.ts -t 'fully settles a custom profile'` passed post-fix (vs. ~30% failure pre-fix), and the full file's 18/18 tests pass — this predates the `usePolling` regression and re-validates unchanged under the re-stat design, since neither touches the reload logic itself. After switching to the re-stat safety net: `packages/boot/app-boot/tests/user-patches.spec.ts` and `hmr-config.spec.ts` pass repeatedly in isolation, and a full-suite `vitest run --coverage --maxWorkers=2` pinned to 2 CPUs (the same load that caught the `usePolling` regression) completes without either test failing.
